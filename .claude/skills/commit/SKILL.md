# commit

변경사항을 읽고, 의미 있는 단위로 쪼개고, 한국어 컨벤션 메시지로 커밋한다. 커밋 히스토리는 나중에 변경 이유를 찾는 기록이므로 "무엇을 왜 바꿨는지"가 한 줄에 드러나야 하고, 서로 다른 목적의 변경이 한 커밋에 섞이지 않아야 한다. 사용자가 커밋을 요청한 것 자체가 승인이므로, 별도로 확인을 구하지 않고 분석부터 커밋까지 한 번에 진행한다.

## 절차

### 1. 변경사항 분석

다음을 병렬로 실행해 현재 상태를 파악한다.

- `git status` — 수정/추가/삭제/untracked 파일 확인
- `git diff` (unstaged)와 `git diff --staged` (staged) — 실제 변경 내용
- `git log --oneline -10` — 이 저장소의 기존 메시지 스타일 확인 (기존 관례가 있으면 아래 규칙보다 우선하지 않되 참고)

변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다. diff가 매우 크면 파일별 `git diff --stat`으로 윤곽을 잡은 뒤 필요한 파일만 자세히 읽는다.

비밀 정보(`.env`, 키, 토큰, 인증 파일)나 빌드 산출물(`node_modules`, `dist` 등)이 포함돼 있으면 커밋 대상에서 제외하고 사용자에게 알린다. 한번 커밋된 비밀은 히스토리에 남기 때문이다.

### 2. 논리적 단위로 분류

변경 파일과 hunk를 "하나의 목적"을 기준으로 묶는다. 판단 기준:

- 기능 추가, 버그 수정, 리팩터링, 설정/문서 변경은 서로 다른 커밋으로 나눈다.
- 한 기능을 위해 함께 바뀐 코드·테스트·타입은 같은 커밋에 둔다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 `git add -p` 등으로 나눌 수 있는지 검토하되, 지나치게 쪼개 복잡해지면 하나로 묶고 이유를 설명한다.
- 변경이 작고 목적이 하나면 억지로 나누지 않고 커밋 1개로 한다.

### 3. 한국어 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

(선택) 본문: 왜 바꿨는지, 주의할 점
```

type은 다음 중에서 고른다.

| type | 용도 |
|------|------|
| feat | 새로운 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 빌드·설정·의존성·문서 등 기타 |

규칙:

- 요약은 50자 내외로, 명사형 또는 `~추가`, `~수정`, `~개선`처럼 간결하게 끝낸다. 마침표는 붙이지 않는다.
- "수정함", "업데이트" 같은 모호한 표현 대신 대상과 효과를 쓴다. (나쁜 예: `fix: 버그 수정` / 좋은 예: `fix: 빈 props일 때 컴포넌트 생성기가 중단되는 문제 수정`)
- 요약만으로 이유가 불분명할 때만 본문을 추가한다. 본문은 "무엇"이 아니라 "왜"를 적는다.
- 위 4개에 맞지 않는 변경(테스트만 추가, 스타일 등)은 가장 가까운 type을 쓰고, 테스트·문서는 보통 `chore`로 둔다.

### 4. 바로 커밋

승인을 기다리지 않고 분류한 순서대로 바로 커밋한다.

- 커밋마다 해당 파일만 명시적으로 `git add <파일>` 한다. `git add -A`/`git add .`는 계획에 없는 파일을 끌고 들어가므로 피한다.
- 메시지는 HEREDOC으로 전달해 줄바꿈과 한글이 깨지지 않게 한다.
- 환경에서 커밋 메시지 끝에 붙이라고 지정한 attribution(Co-Authored-By 등) 줄이 있으면 그대로 따른다.
- 모두 끝나면 `git log --oneline -N`으로 결과를 보여주고, 각 커밋의 메시지와 포함 파일을 간단히 요약한다. 사용자가 사후에 메시지나 분류를 바꾸고 싶다면 그때 수정(`--amend`, reset 등)을 제안한다.

## 하지 않는 것

- 승인 절차는 없지만 범위는 로컬 커밋까지다. 요청하지 않은 `git push`, 브랜치 생성, `--amend`, `--force`, `--no-verify`는 하지 않는다.
- pre-commit 훅이 실패하면 우회하지 말고 원인을 보고한 뒤 수정 방향을 제안한다.
- 이미 staged된 파일이 있으면 사용자가 의도한 구성일 수 있으므로, 분류 시 이를 존중하고 계획에서 명시한다.
