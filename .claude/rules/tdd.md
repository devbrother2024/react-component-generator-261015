# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

**프로젝트별 규칙 우선:** 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 있으면 **그 규칙이 이 파일보다 우선한다.** 이 파일은 기본값(fallback)이다.

## 1. 적용 기준

### 반드시 TDD를 적용하는 대상

- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이, 데이터 변환)
- **API** (라우트 핸들러, 요청/응답 처리, 에러 분기)
- **유틸리티 함수** (순수 함수, 파서, 포맷터)
- **버그 수정** (먼저 버그를 재현하는 실패 테스트를 작성한 뒤 고친다)

### TDD가 불필요한 대상

- **타입 정의** (type, interface)
- **설정 파일** (tsconfig, vite.config, eslint 등)
- **순수 UI** (로직 없는 마크업, 스타일링)
- **SQL** (스키마, 마이그레이션)

경계가 모호하면 **적용하는 쪽**을 택한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 오타, import 오류, 문법 오류, 잘못된 셋업으로 인한 실패는 RED가 아니므로 테스트를 고쳐 다시 실행한다.

### GREEN: 최소한의 코드로 통과

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI:** 지금 테스트가 요구하지 않는 기능, 옵션, 추상화를 추가하지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체 실행으로 확인한다.

### REFACTOR: 구조 개선

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지한다.** 변경마다 테스트를 다시 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 반복

다음 동작에 대한 **RED로 돌아간다.** 요구사항의 모든 동작이 테스트로 덮일 때까지 반복한다.

## 3. 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 해당한다.
- 삭제한 코드를 복사해 붙여넣지 말고, 테스트가 요구하는 만큼만 새로 작성한다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 단순하다. 비용이 거의 없고, 나중에 복잡해질 때 회귀를 막아주는 안전망이 된다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 이미 구현에 맞춰져 바로 통과하므로 아무것도 증명하지 못한다. 그리고 그 "나중"은 오지 않는다. |
| "시간이 없다" | 디버깅과 회귀 수정에 드는 시간이 테스트 작성 시간보다 크다. 급할수록 실패를 빨리 잡는 TDD가 빠르다. |
| "삭제하면 낭비다" | 매몰 비용 오류다. 검증되지 않은 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. 삭제 후 재작성은 보통 더 작고 정확하다. |
| "프로토타입이다" | 프로토타입은 자주 프로덕션이 된다. 버릴 코드라면 테스트도 가볍게 쓰면 되고, 로직이 있다면 이 규칙은 그대로 적용된다. |
